# remote-build-offload：整板构建推到更空闲的机器上跑，两种实现策略并行，用已知答案校准一次再信它

类型：提示词工作流 + 脚本模板（`compare_builds.sh` 构建对比、`remote_run_template.sh` 远端脱钩启动器）+ 检查清单。

## 适用场景

- 本机被别的任务占满（我们当时 48 核负载约 41、常常只剩约 22 GB 可用内存），一次整板构建 87–111 分钟；
- 手边有另一台装了同大版本 Vivado、许可证对你的器件可用的机器；
- 时序在边缘（WNS 只有几个 ps 的余量），同一份输入换实现策略可能一过一不过。

## 用法

1. **先确认远端可用**：Vivado 版本（我们远端是 2022.2.2，本机 2022.2）、器件许可证（看日志 `Got license for feature 'Synthesis' and/or device ...`）、可用内存与线程余量。
2. **输入原样推过去**：源码用 `git archive <commit>` 出包（只读副本，不是 git 仓）；IP 目录用 rsync；各核的 export.zip 按内容 sha256 存放。
   构建 Tcl 里不要写死绝对路径——全部由环境变量给，远端只改写环境变量里的路径，源码逐字节相同。
3. **远端脱钩启动**：`remote_run_template.sh <build_dir> <env_file> <build_tcl>`（`setsid nohup`，记 pid、rc、LEDGER）。ssh 断线、本机会话关闭都不影响构建。
   停构建只按 pid 停，不用 `pkill -f`。
4. **关键构建两种策略并行**：默认策略一份，`place ExtraTimingOpt / phys_opt AggressiveExplore / route AggressiveExplore` 一份，谁过时序用谁。
   共享机上自己的线程总数设上限（我们是合计 ≤ 16 线程、可用内存 ≥ 16 GB 才起）。
5. **拉回后必须判时序**：rc=0 只说明 Vivado 跑完，负 WNS 也是 rc=0。
6. **第一次用之前，拿一个本机构建过的版本当已知答案校准**：同 commit、同核 zip（sha256 一致）、同环境变量在远端重跑，用 `compare_builds.sh <本机构建> <远端构建>` 对比。
   `compare_builds.sh` 自身先校准：自己对自己全 IDENTICAL；拿两个已知不同的构建对比，要能报出 DIFFERS。

## 失效条件

- 远端 Vivado 小版本不同时，比特流哈希不会和本机相同，布局布线也不逐位一致；回归判据只能是功能等价（地址表、hwh、块设计）加时序和利用率。
- 输入很大、网络很慢时推送会成为瓶颈（我们实测约 2 MB/s，首次推送约 45 MB 用 42 秒，之后只有增量）。
- 构建后要在本机跑的检查（功耗报告、CDC 护栏）需要把约 240 MB 的 routed.dcp 拉回来。
- 远端是共享机：不用 GPU、不装软件、不用 sudo、不碰别人的目录，旧构建目录要定期删。
- `compare_builds.sh` 默认按我们的块设计名（`m7_pl`）和时钟名找文件、读数，换设计要改文件名列表和时钟名。
- `remote_run_template.sh` 是从我们的启动器改写的通用版，**没有在提交包内重跑**；`compare_builds.sh` 在本包内用三组假构建目录做过自测（自比全 IDENTICAL、只差时间戳/路径行判为同、改了 hwh 和 LUT 判为 DIFFERS 并算出 +10.00%）。

## 已验证的效果（校准构建：同一 commit、同核 zip，本机增量 vs 远端从头）

| 项 | 本机（增量，默认策略） | 远端默认策略从头 | 远端加强时序策略从头 |
|---|---|---|---|
| 墙钟 | 111 分钟 | **29.5 分钟** | 34 分钟（与另一构建并行，合计 16 线程） |
| 综合 / 布局 / 布线 | 17 / 15 / 60 分钟 | 6.3 / 7.3 / 11.4 分钟 | 7 / 6 / 16 分钟 |
| 地址表 | — | 逐字节相同 | 逐字节相同 |
| hwh、块设计 | — | 只差时间戳、DPU 构建时刻参数和两个主口编号 | 同左 |
| LUT / FF | 77,316 / 99,606 | 76,805（−0.66%）/ 100,315（+0.71%） | 76,847 / 100,241 |
| BRAM / URAM / DSP | 124.5 / 35 / 299 | 相同 | 相同 |
| setup WNS | +0.006 ns | **−0.006 ns（没过）** | **+0.022 ns（过）** |

- 远端约 3 倍快。默认策略差 6 ps 没过（5 个端点全在 600 MHz 的 DSP 时钟域），同一份输入换加强时序策略过了——这就是"两种策略并行"的由来。
- 没过的竞争解释有两个：从头实现的布局随机性，或 2022.2.2 与 2022.2 的时序算法差别。区分它们需要本机也从头跑一次同配置，我们没做。

## 从哪些失败里总结出来

- 整板构建排队是赛程里最大的时间浪费：一次 DPU 探针布线 3 小时以上，同时还有 4 个 HLS 包在排队。原来"同一时刻只跑一个大构建、等宿主完全空闲"的规矩保守过头。
  由此还定了三条本机提速规矩：小构建（csynth / cosim / OOC）走几个原子取用的构建槽、按可用内存把关；改动小的比特流用增量实现（`read_checkpoint -incremental`）；
  探针构建布局后先看时序，WNS 低于阈值就以退出码 3 提前停，不进布线。
- 第一次远端校准里默认策略差 6 ps 没过时序，而本机同一配置余量也只有 +6 ps——单策略构建在边缘配置上不可靠。
- 环境差异要先列清再比对：远端是 Ubuntu 24.04、时区 UTC（日志时间戳与本机差 8 小时），Vivado 多一个更新包。我们把这些差异写进校准记录，避免把它们误当成构建差异。
