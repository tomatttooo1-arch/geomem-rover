# board-e2e-measure：上板安全与端到端时延测量协议（嵌入式 Linux 板卡 + PL 加速 + DPU）

类型：踩坑清单 + 案例模板（`criteria_template.md` 预注册判读模板）+ 校验脚本（`seg_latency.py` 分段汇总，带自测）。

## 适用场景

- 在 KV260 一类的 Zynq UltraScale+ 板子上跑整条应用链（相机 → 前处理 → DPU 推理 → 后处理 → 规划），要报"相机到结果"的端到端时延、帧率和功耗；
- 让智能体或队友远程操作板子，一旦把板子弄死需要有人到现场断电；
- 想把"模块时延之和"和"端到端实测"对上，或者解释为什么对不上。

## 用法

**A. 上板安全（每次上板前过一遍）**
1. **不在板上原生编译大目标，宿主交叉编译后再拷上去。** 我们一次整机卡死就发生在板上链接一个大可执行文件期间（见"失败"）。
2. 加载比特流后**先读回构建号寄存器**（BUILD_ID），不对就不测。
3. 写好"卡死处理"：ssh 连续 6 次失败 ⇒ 立刻停，不重试、不重新加载，写记录，等人到现场断电。
4. 板上卡死后的定位只读日志、不先加载任何新比特流：看上一次开机的持久化 journal、关键文件的 inode 时间、产物目录里哪些步骤的输出存在——
   按"哪一步的产物在、哪一步的不在"定位卡在哪一段，而不是猜最可疑的新东西。

**B. 端到端时延测量**
1. **先写判读规则再测量**（`criteria_template.md`）：三个数的定义、预热时长、有效帧数下限、丢帧率上限、时间戳单调性门、"PL 真在用"的检查。写定后不改。
2. **所有时间戳用板上同一个单调时钟**（`CLOCK_MONOTONIC`，纳秒），起点统一为"相机拿到这一帧"的时刻，每一级记一个时间戳。
3. **汇总脚本先在已知答案上校准**：`python3 seg_latency.py --selftest`（人为把末级时间戳整体 +5 ms，结果必须正好多 5 ms；插一个违反单调的时间戳、对调两帧顺序，都必须被查出）。
   然后 `python3 seg_latency.py data.csv --stages t_cam_ns,t_prep_ns,t_dpu_ns,t_post_ns --warmup-s 10`。
4. 报数时分段报（等待取帧、PL 前处理、排队、DPU、CPU 后处理），并和"模块单测之和"放在一起对照。
5. **推理线程数要单独测**：多线程（双缓冲）提高帧率，但每帧在 DPU 段的等待里会包含另一帧的推理时间，单帧时延会接近翻倍。要报时延就补测单线程。

## 失效条件

- 跨设备（板子和宿主、两块板子）的时间戳不在同一个时钟上，不能直接相减；本协议只管单板内。
- `seg_latency.py` 只检查时间戳的单调性和帧序，不检查时间戳打在了正确的位置——打点位置要读代码确认。
- "不在板上原生编译"是规避措施，不是根因结论：那次卡死的根因没有坐实（见下）。
- 功耗只测了 SOM 5 V 轨（INA260），不含相机等外设。

## 已验证的效果

- **双缓冲让单帧时延翻倍**（512 输入档，两条链同跑，板上单调时钟，去掉前 10 s 预热）：
  | 推理线程 | 相机 → 物体框 中位 / p95 | 帧率 | DPU 段中位 |
  |---|---|---|---|
  | 2（双缓冲，默认） | 147.7 / 163.4 ms | 15.63 帧/秒（DPU 本体上界 15.68） | 116.8 ms ≈ 2 × 63.8 ms |
  | 1 | **99.4 / 106.8 ms** | 13.58 帧/秒 | 64.1 ms |
  模块单测之和约 67.5 ms；双线程时单帧时延远高于它，而帧率贴着 DPU 上界——这是用时延换吞吐，不是哪里慢了。单线程时多出来的主要是等待取帧约 26 ms。
- **汇总脚本校准**：我们实际用的汇总脚本先在宿主空跑的数据上和另一套报表对过（时延和帧率相同），人为把后处理时间戳加 5 ms 结果正好多 5 ms，插一个违反单调的时间戳和一处帧序对调都被查出。
  本目录的 `seg_latency.py` 是按同样思路为提交包重写的通用版，`--selftest` 在本包内跑过：`SELFTEST PASS (+5ms shift: seg 5.000 ms, total 5.000 ms)`。
- **卡死定位协议**：靠只读日志把一次整机卡死定位到"板上链接 dpu_rx 期间"：dpu_rx 输出文件的 inode 已创建、长度为 0（链接器正在写输出），时间晚于上次开机 journal 的最后一条；构建日志只有前 4 个目标成功；
  加载比特流那一步的目录、固件拷贝都不存在——所以和新比特流、新的寄存器配置脚本都无关（它们根本没执行）。

## 从哪些失败里总结出来

- **整机卡死**：一次冒烟测试里板子失联，网口有载波但串口不回。我们一开始怀疑新比特流里第一次上真板的东西（DPU 时钟门控、新寄存器配置脚本）。
  只读日志后发现卡死发生在冒烟链第 2 段"板上编译"，链接 dpu_rx 的时候，比特流根本没加载。随后单独重编一次同一目标（73 s，内存最低 3.23 GB，温度最高 36.1 °C）**没有复现**，
  根因未坐实（竞争解释包括显示栈报错叠加、供电跌落等）。规矩因此是"不在板上编译 + 有失联处理预案"，而不是"某个模块有问题"。
  另一个教训：**网口有载波只能说明载板有电，不能说明 SOM 还活着**（网口 PHY 在载板上）。
- **时延对不上**：第一次端到端实测相机到物体框中位 147.7 ms，而模块之和只有 67.5 ms。分段后发现 DPU 段是单帧推理时间的两倍——两个推理线程同时排在 DPU 队列里。
  没有分段时间戳就只能猜。
- **仪器本身出错**：汇总脚本如果没先在已知答案上校准，一个时间戳打错位置或帧序错乱会直接变成"结论"。所以先做 +5 ms 和单调性的判别力测试。
