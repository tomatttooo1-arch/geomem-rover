# hls-microcode-area：HLS 核超面积时，先做硬件架构再写码；控制密集的长算法用"一个共用运算单元 + 微程序"

类型：提示词工作流 + 案例模板（`arch_template.md` 是写给智能体的架构设计模板，`coding_rules.md` 是五条写码规矩）。

## 适用场景

- 一个 HLS 核的 OOC LUT 远超预算，而它的 C 代码是**很长的标量控制逻辑**（几百个加、减、比较、分支，彼此串行，没有大规模数据并行）。
  典型症状：csynth 报告里加法器、比较器、选择器的个数和 C 代码里运算的个数差不多——HLS 给每个运算单独造了一份硬件。
- 时延预算比较宽（我们的例子允许每帧 ≤1 ms，100 MHz），可以拿拍数换面积。
- 你让智能体（或自己）"把软件代码交给 HLS 再调 pragma"已经调过一轮，面积还是降不下来。

## 用法

1. **先写架构，后写码**（`arch_template.md`）：数据通路框图、指令格式与位宽、寄存器堆大小、ROM 深度、每段算法映射成多少条微指令与拍数、
   **逐部件手算 LUT/FF/DSP/BRAM**。手算合计要在预算以内才往下写码。控制逻辑（选择器、地址生成、相位控制）按每处几十 LUT 留量，别只算数据通路。
2. **共用运算单元**：只放一个 64 位加法器（加、减、比较、分支条件、访存地址、除法步、开方步都走它）、一个乘法器（放 DSP）、一套移位器、一个选择器；
   算法写成微指令一条条在它上面跑。硬件量变成固定值，算法长度只占 ROM（BRAM）。
3. **微程序用生成器，不手写**：一份可读的操作表 → Python 生成器出 ROM 初值头文件；同一份操作表在 Python 里解释执行作为参考，与原 C 模型逐位对照；常数直接从原 C 头文件解析，不手抄。
4. **校验**：原 C 模型的录制调用逐位回放；改一条微指令必须被抓到（阳性对照；注意不是每条改动都能当阳性对照，见下）；联仿子集逐字节一致；最后 OOC 实测。
5. **csynth 后逐项对手算**，任何一项超手算 1.5 倍先按 `coding_rules.md` 改，再跑 OOC。对外数字一律以 OOC 为准。
6. 先判断适不适合（见"失效条件"）：如果核里有大块数据并行的内层循环，那部分要留成专用硬件单元，微程序只管控制。

## 失效条件

- **数据并行为主的核不适用**：图像、深度图、栅格扫描这类每拍处理一个像素的流水，改成微程序会让拍数暴涨，该用流水 + 端口加宽。
- **微程序 + 大的专用单元，不会自动省面积**。反例：搜索核第一版微程序化（m1）保留了两个大专用单元（扫描、信念更新），csynth 估计 10,485 LUT，
  手算只有约 4,000，每个部件都超手算 1.5 倍以上；原来的直写版 OOC 是 9,683 LUT。超支在加法/比较/移位表达式和多路选择上（多个模块共用同一片存储，
  各自的读口在顶层变成大选择器），不是乘法。这一版还在继续压，**没有得出"微程序对它有效"的结论**。注意 10,485 是 csynth 估计、9,683 是 OOC 实数，口径不同，不能直接相减。
- 拍数会变多（我们的例子里每条微指令 5 拍）。实时性要求紧时先算拍数预算。
- 生成器 + 参考解释器 + 顺序器三者一致，只证明它们彼此一致，不证明原 C 模型的意图被正确表达；必须对原 C 模型的录制回放。

## 已验证的效果

例子：语义记忆核（多帧观测的配对、融合、存在度结算），出处为记忆核微程序化工作包的 README 与 ARCH：

| 版本 | OOC LUT | FF | DSP | RAMB36 | 布线后时序 |
|---|---|---|---|---|---|
| 上一版：C 代码直接 HLS，已调过 pragma | 9,180 | 9,041 | 55 | 5 | 9.08 ns |
| 共用运算单元 + 1,961 条微指令 + BRAM 端口外壳 | **1,487**（−84%） | 909 | 4 | 4（另核外 2） | 8.0 ns（100 MHz 下 WNS +2.0 ns） |

- 手算 1,450 LUT，OOC 1,487，差 3%；csynth 估计 2,201 → 按规矩改写后 1,964 → OOC 1,487（csynth 估计偏大）。
- 功能：14,886 次录制调用（实车 9,383、压力流 5,503）结果块与原 C 模型逐字相同；联仿 531 次逐字节相同。
- 阳性对照：把关联半径那条微指令的立即数减半，531 次里 236 次不一致，被抓到。另有三处改动（内点下限、融合舍入、命中增量）在这批向量里没引起差异——
  对应分支没被触发或被饱和吃掉，所以**不能当阳性对照**。教训：阳性对照要先确认它在你的测试向量上真的会改变输出。
- 代价：每帧时延实车中位 0.42 ms、最坏 0.81 ms，压力流最坏约 1.39 ms（按 5 拍/条推算，联仿 531 次与推算一致）；板上耗时没测。
- 降面积的来源有两部分：架构改写（共用运算单元）和外壳改 BRAM 端口（见 `../axi-bram-shell/`）。两者是一起做的，没有单独拆开量各自贡献。

## 从哪些失败里总结出来

- 记忆核上一版是"C 代码直接 HLS"，OOC 9,180 LUT，预算 2,500。拆开看：约 560 个 C 运算被做成 186 个加法器、179 个比较器、154 个选择器；
  AXI-Lite 数组外壳 1,418 LUT，LUTRAM 槽表写口 1,427 LUT。调 pragma 改变不了"每个运算一份硬件"这个结构。
- 取路径核实测：手算新增 363 LUT，OOC +630（1.7 倍），HLS 估计 2.5–3 倍；超出全在控制与选择逻辑，算术部分基本贴预算。由此得出五条写码规矩（`coding_rules.md`）。
- 检测后处理核 csynth 估 8,659 LUT、OOC 实数 3,703（2.34 倍）——有坏处的面积刀要先拿 OOC 实数再决定做不做。
- 搜索核照搬微程序（上面的反例）：说明"微程序"本身不是答案，关键是先判断核的形态，再决定哪部分共用、哪部分留专用硬件。
