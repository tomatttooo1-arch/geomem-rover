# subagent-brief：主控 + 执行子代理的分工方式——有界任务书、盘上交接、按上下文轮换、主控复核验收

类型：提示词工作流 + 案例模板（`brief_template.md` 任务书、`handover_template.md` 交接单、`acceptance_checklist.md` 验收清单）。

## 适用场景

- 用 Claude Code（或其他能派子代理的智能体）做多小时、多步骤的硬件工程：一个主会话负责分析、决策、验收，多个子代理执行具体工作包（写一个核、跑一次构建、做一次板上测量）；
- 工作会跨过多次上下文压缩或额度切断；
- 需要事后能说清"每个数字从哪来、谁跑的、按什么判据判的"。

## 用法

1. **按步切包**：一个子代理只领一个有界步骤（例：一个核的一轮架构 + 实现 + 校验，一次整板构建，一次板上测量），预计 ≤ 2–3 小时。
   多步串联的等待交给脱离会话运行的脚本（`setsid nohup` + 账本），代理只做"起链 / 判一步 / 写账本"的短活。
2. **任务书写五样**（`brief_template.md`）：目标、输入（上一棒的文件路径和节号）、门（在测量之前写定）、规矩（共享资源怎么取、什么不能碰）、期限。
   主控已定的事写成"裁定，不再讨论"，避免代理在执行中重新争论路线。背景只给指针，不复述。
3. **输出节流写进任务书**：tail / grep，不 cat 大日志，长内容落文件再引路径。
4. **上下文到约 300k 就轮换**：代理停手写 `HANDOVER.md`（`handover_template.md`），提交后结束；下一棒是**新代理 + 新任务书**，只读 HANDOVER 接续，不用"继续发消息给旧代理"续跑。
   主控不能只靠代理自觉，每次收到进度通知时顺手量一下在跑代理的上下文用量。
5. **验收按清单复核**（`acceptance_checklist.md`）：关键数字由主控用同一套工具重跑，不采信代理自报。

## 失效条件

- 任务本身很小（几次工具调用）时，写任务书和交接单的开销大于收益，直接做。
- 任务之间强耦合、需要频繁来回讨论时，拆包会制造大量交接成本；先由主控把方案定下来再拆。
- 300k 这条线是我们在 Claude Opus 系列模型上的经验值（我们先后用过 270k、300k、320k、330k），换模型或换窗口大小要重新定，但每份任务书里要写死一个数。
- 轮换只解决"上下文太长导致质量下降"，不解决任务书本身写错的问题。

## 已验证的效果

- 反例：早期一条线上，一个子代理从两档预算表一路做到引擎、单测、全量评测、修复、重跑，跨了六次额度切断续跑，累计约 94 万 token，最后以 "Prompt is too long" 终止在半截；
  后半段"仪器错误冒充结论"复发了五次（变量默认值写错、包导入副作用、变量定义在被跳过的分支里、把"文件存在"当成"已完成"、首个匹配读到不存在的路径）。
- 采用本流程后的实例：
  - 记忆核微程序化包按任务书一次交回并过门（OOC 1,487 LUT，门 2,500），README 带手算 / csynth / OOC 三列对照、五项校验和未完成项；
  - 搜索核微程序化包在交接线轮换，第一棒留下的 HANDOVER 写清了现状、已验证项、当前数字、下一棒顺序和坑，下一棒直接从"按 csynth 逐项压"开始；

## 从哪些失败里总结出来

- 上面的 94 万 token 长代理：质量随上下文变长明显下降，而续跑只是把更长的历史再喂一遍。
- 主控自己漏量：有一次主会话在上下文压缩前后没有去量在跑的代理，一个判读代理跑到了约 445k；另一次断线后用"继续发消息"续跑旧代理，三个代理同时越线（364k–436k）。
  所以清单里写了"压缩恢复后先量一遍所有在跑代理"和"过线的不续跑，新开"。
- 只在任务书里写"到 180k 收尾"不够——代理照样跑到 578k、334k。靠得住的是主控在心跳里直接量，以及把任务切得更小。
