## 3. 纠错过程

代理没有只看"板子没重启"，而是按判据原文逐项核对"四个进程 pid 全程不变"，由此查到原因（README "上板时发现并已修的问题"一节）：

> 1. **kv_server 停不干净**：启动行写成 `(cd R && nohup python … &)`，`$!` 拿到的是子 shell，停止时 TERM 了子 shell，python 服务进程活了下来、占住 47800 端口，导致下一次启动的 kv_server 绑定失败（第二次运行……因此没有深度链数据）。两个残留进程都已按 pid 停掉。修法：先 cd 再后台起服务本身……
> 2. **重复加载比特流**：GO 要求 m5 已在就不重载，但 `xmutil listapps` 在 board_bringup 加载后 Active_slot 仍显示 −1，判断失效，前两次运行都重新加载了一次 m5……修法：sysinfo UIO 节点存在时读 BUILD_ID，等于期望值就不重载；最终两次复跑日志均为 "already loaded: not reloaded"。
> 3. dpu_rx 按 RUN_S 计时自停，改为跑到 stop 为止，RUN_S 只管采样器。

判据本身的调整（连续时长 600 s 改 300 s）是按"演进只追加"的规矩在 CRITERIA.md 新开一节写明的，原判据不改：

> - C1 改为 ≥ 300 s（整机运行 300 s，原 600 s）；C2–C6 不变。

主会话验收后又做了一处改动（CONTROL.md）：

> 13:31 GOLIVE0 交回（C1–C4 过，已修脚本缺陷；PL 后处理 0.448 ms、7.13 帧/秒；A53 前处理 18.3、后处理 6.70 ms；矩形模型 DPU 9.35 帧/秒；整链 5.89 W）。主控把启动脚本默认改成 --post pl……

即把识别后处理默认切到 PL 核（实测 0.448 ms，CPU 版 6.70 ms），保证提交版本"一条命令起整机"时跑的就是硬件后处理。
